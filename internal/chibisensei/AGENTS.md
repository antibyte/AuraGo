# Chibi Sensei package contract

## Purpose

Domain package of the Chibi Sensei desktop app (guided studio for training small language models): the SQLite store, rows, history with undo, checks, split, presets, plan, profiles, imports, documents, export, the job runner, the event hub, the prompts, schemas and parsers of generation and cleaning, and the Kaggle training runs (trainer script and lock, job spec, notebook, snapshot, log and output parsers, run store, consents, plan tokens, preflight evaluation, report scoring, the `KaggleDriver` interface and the run orchestrator). It never imports `internal/server`, `internal/desktop` or `internal/llm`; it imports `internal/kaggle`, `internal/config`, `internal/security`, `internal/fileutil` and its own `trainer` package. The model call reaches it only through values the server hands in (`wrap func(string) string` for untrusted text, parsed answers as strings), and Kaggle only through the `KaggleDriver` the server implements (`internal/server/chibi_sensei_kaggle.go`). Spec: `docs/superpowers/specs/2026-11-22-chibi-sensei-design.md`; plans: `docs/superpowers/plans/2026-11-22-chibi-sensei-p1*.md` and the P2 plan files beside them.

## Ownership

- `data/chibi_sensei.db`, schema v1 (`schema.go`): every table of the spec (the run, metric, artifact and base-GGUF tables belong to the training runs) plus `batches` (`open`, `undone`, `row_count`), `suggestions` (`row_rev`, `applied`), `checks.ready` and `row_history.op` / `after_rev`. `dataset_rows.id` is `AUTOINCREMENT`, so an id is never reused after a delete.
- `profiles/*.json` and their embedded catalog (`profiles.go`); check IDs and message keys (`checks.go`); the prompt texts and JSON schemas of `generate.go`.
- Files: `store.go` open and size; `projects.go` CRUD, steps, delete; `rows.go` validation, structure, hashes, labels; `rowstore.go` add, update, page, filter, select, bulk, delete; `history.go` batches, undo, dedupe; `confirm.go` delete-preview tokens; `checks.go`, `split.go`, `presets.go`, `plan.go`, `suggest.go`, `lang.go`, `tokens.go`; `imports.go`, `documents.go`, `export.go`; `jobs.go`, `events.go`; `generate.go` prompts, schemas, parsing, chunking, the suggestions store and the daily cap.
- Training files:
  - Training (P2): `trainer/` (`chibi_train.py` and `requirements.lock`, embedded by `trainer/embed.go`; lock keys `pip` (repeatable, exact `name==version`), `transformers`, `llama_cpp_tag`, `llama_cpp_url`, `llama_cpp_sha256`, each other key once); `jobspec.go` (`job.json` v1), `notebook.go`, `snapshot.go` (split files, marker, `Run12`, `DatasetSlug`, `NotebookSlug`), `logparse.go`, `outputs.go`; `runs.go` (run model, states, API view), `runstore.go`, `consents.go` (consents and settings), `plantoken.go`, `preflight.go`, `quota.go`, `report.go`, `driver.go` (`KaggleDriver`, request IDs, job statuses); `reconcile*.go` (orchestrator), `artifacts.go` (storage layout, verified copies, `base_gguf`), `gguf.go`; `testdata/` (goldens, proof data); tests `fakekaggle_test.go`, `reconcile_test.go`, `reconcile_restart_test.go`, `proofbundle_test.go`.
- Storage directory:
  - `data/chibi_sensei/` with `runs/<run>/` (snapshot, notebook, `out/` small outputs and `log-tail.txt`), `models/<run>/` (GGUF, adapter) and `base/` (shared base GGUFs). Not part of AuraGo backups; only `chibi_sensei.db` is.

## Local Contracts

- The store uses one connection (`SetMaxOpenConns(1)`). Inside a transaction use `tx`; never call a store method, the hub or a job's `report` while a `*sql.Rows` or a transaction is open, and never hold a transaction across a model call. Page by `seq > last` with `LIMIT 1000`.
- Every row mutation bumps `data_rev` in the same transaction and calls the notifier after commit. A project change to recipe, task_kind, labels, profile, preset or overrides bumps `data_rev` too.
- A delete of rows (bulk, dedupe, delete by filter) resolves the selection and deletes in one transaction; a delete token binds project, canonical select and `data_rev`.
- History keeps 50 batches. A batch a running job writes (`AddRows` with a caller-named `BatchID`) is `open` and never pruned; the job must call `CloseBatch` when it ends, whatever its outcome (`RunImport` and the generation job do). `AddRows` into an undone batch returns `ErrAlreadyUndone`; a job that meets it ends as cancelled (generation and `RunImport`, which keeps nothing of the undone batch).
- Undo is refused with `ErrUndoConflict` when a later change touched a row of the batch: a row the batch inserted or updated must still have the `after_rev` the batch left, a row it deleted must still be gone. Label, the local flags and `est_tokens` are derived data: undo recomputes them from the restored content under the project's current recipe and task kind (`deriveFields`, as `AddRows` and `UpdateRow`) and clears the cross-row flags, so a recipe change (`recomputeRows` does not bump `rev`) is never undone by an older snapshot.
- Hashes normalize NFC, lower case and collapsed whitespace. The token estimate is a fixed formula in `tokens.go`. The split is by `sha256(seed || id)`. Flags: local flags on every write, cross-row flags only from `RunChecks`.
- Untrusted text (rows, documents) reaches a prompt only through the `wrap` func, and the goal text and the user's instructions are never wrapped. Model output is untrusted: `ParseGenerated` and `ParseClean` decode strictly, validate every row with `ValidateRowInput` and `StructureProblems` (the validator of table edits and imports), cap the count, and `ParseClean` never lets an id outside the batch through.
- Cleaning: `accept "all"` (nil) applies only `fix`; a `drop` needs its row id listed. `ApplySuggestions` skips, and counts as skipped, a suggestion whose row is gone or whose `rev` differs from the recorded `row_rev`, so it never overwrites a newer edit. It writes one batch of kind `clean` with the per-row `after_rev`.
- The daily cap (`settings` key `generator_daily`, local day) is reserved up front by `ReserveDaily` and the unused part refunded by `ReleaseDaily` (a count of another day is left alone).
- Job outcomes: a job whose own deadline passes ends `failed` with `timeout` (a user cancel or shutdown stays `cancelled`). `generate` and `clean` jobs hold one of `llmJobSlots` (2) runner slots while they run; without a free slot the job is stored `queued`, waits with its context (so a cancel works at once) and turns `running` when it gets one. The slot is freed right after the job function returns, panic included. A queued job cancelled before it got a slot still calls its function, with the done context and without a slot (and releases none); the function checks the context first and returns, so only its defers run (refund of the daily reservation, release of the route).
- Limits: `Hub.Subscribe` returns `ErrTooManyStreams` above 16 subscribers per project or 64 in total. `AddOptions.Full` (jobs) is checked before every batch of rows: `ErrStorageFull`, which the job maps to the code `storage_full` and keeps the rows added so far. A JSONL line or CSV record over 1 MiB (`importLineMax`) is skipped and reported as `chibi_sensei.import.line_too_long`; the CSV reader stops a record at the cap and resumes after it (`csvLimitReader`, `csvRecordEnd`; the quote-parity resync is only right for strict quoting). CSV quoting is strict (`LazyQuotes = false`): a record the reader rejects (bare quote, bad quoting) is skipped and reported as `chibi_sensei.import.bad_csv` with its line, and the import goes on with the next record. A document file is read up to `MaxDocumentBytes`.
- Profiles are `experimental` with a non-empty `unverified` list until their Kaggle proof run passed (spec "Testing", manual proof run); `verified` needs an empty `unverified` list and the `verified` block (`ValidateProfile`).
- Trainer contract: stages are `TrainerStages` (boot, env_check, data, install, load_base, converter, base_eval, train, tuned_eval, save, gguf, manifest); the parsers reject other names. `@@chibi` lines carry `seq` except the wrapper's exit line; metric lines carry `kind`. Outputs are flat files in `/kaggle/working` named by the `Out*` constants (`chibi-status.json`, `chibi-manifest.json`, `chibi-metrics.jsonl`, `chibi-eval_samples.jsonl`, `chibi-model-q8_0.gguf`, `chibi-base-q8_0.gguf`, `chibi-adapter-model.safetensors`, `chibi-adapter-config.json`); each manifest kind at most once (`ManifestKindFile`). Dataset files are `r<run12>-{train,val,eval}.jsonl` and `r<run12>-marker.json`; a split without rows has no file. No secret enters `job.json`, the notebook, logs or events; Kaggle log text is scrubbed before it is stored.
- Trainer lock: `trainer/requirements.lock` must carry `llama_cpp_sha256`, the sha256 of the llama.cpp source tarball (64 lower-case hex characters). `ParseLock` and `Lock.Validate` reject a lock without it; the notebook refuses a tarball that does not match it (`gguf_failed`).
- Deterministic outputs: `job.json` and the notebook are deterministic bytes. A change to their builders, the trainer, the lock or a profile regenerates the goldens in the same change. `.gitattributes` keeps LF for `internal/chibisensei/trainer/**` and `internal/chibisensei/testdata/**` (the script hash and the goldens depend on it).
- Runs: one non-terminal run per installation (`CreateRun` → `ErrRunActive`); `DeleteRun` only for terminal runs (`ErrRunNotTerminal`); `DeleteProject` refuses a project with a non-terminal run. `UpdateRun` loads, changes, stores and appends at most one event in one transaction (an empty kind writes none); publish after the commit. Data without a column lives in `remote_json`; absent times are `""`; `last_state` is the last non-terminal state. `run_events.data` shapes: `state {to}`, `stage {stage,state}`, `warn {code,message}`, `error {stage,code,message}`, `kaggle {step,job_id}`, `log {text}`. `since_step` is inclusive and a non-finite loss is never stored. Artifact JSON hides run, project and path; `name` is the base name; artifact IDs are UUID v5 of run and kind. The Kaggle project id is the setting `kaggle_project_id`.
- Plan tokens: plan tokens live in memory (15 min, at most 64, single use) and bind project, run ID, preset and `PlanHash` (plan with `data_rev`, profile SHA, script SHA, owner, machine shape, delete flag).
- Preflight: preflight evaluation is pure: the server collects `PreflightInput`; `KaggleReachable` gates the connection test and the quota read; item IDs, order and args follow the HTTP contract. `PreflightFlagPatch` is the only mapping from flag names to config values. `ParseGPUQuota` stays provisional until a proof run records the real answer.
- Report: `loss` and `perplexity` values may be null. A score with no scored sample is `null` (`ratio4`), never 0; `exact_match` and `label_accuracy` carry nullable `base` and `tuned` with the counts `n` (tuned) and `n_base` (present only when it differs from `n`). A confusion matrix has one row per label and one extra "other" column; samples whose expected answer is no label are left out of `label_accuracy`. `TestScoreReportNoBaseAnswers` covers the null scores.
- Log parsing: `ParseKernelLog` accepts Kaggle's JSON array of stream entries (finished session), the `text/event-stream` body of a running session (`data: {stream entry}` events; `TestParseKernelLogEventStream`, a cut last event is dropped), a tail cut of such an array (entries are found by their `"stream_name"` key) and plain text. `logTailText` joins the entries' `data` text for every form (`TestLogTailTextEventStream`). A plain-text body that contains an embedded stream object keeps its own `@@chibi` lines (`TestParseKernelLogPlainTextWithEmbeddedStreamObject`). Each embedded entry decodes within a window of at most 1 MiB that ends at the next stream key, at most 200000 entries are scanned, and lines over the `@@chibi` line limit are skipped, so the work stays linear (`TestParseKernelLogStreamKeyFloodIsLinear`).
- Orchestrator: one goroutine owns the active run; `Step` is the unit of work, at most one Kaggle mutation and one transition, each an `UpdateRun` with hub events after the commit. Request IDs are `KaggleRequestID(run, step, attempt)`; `unknown` is never replayed (uploads and downloads take a new attempt, `create_dataset` is decided by `get_dataset`, `save_kernel` by `get_kernel_session_status`: answers → untracked, not found → `kaggle_submit_unknown`); at most 3 attempts. Kaggle answers 403 `PERMISSION_DENIED` for a missing resource: `IsKaggleNotFound` (via `kaggle.NotFound`) accepts 403 and 404, and `fakeKaggle` answers 403. Status and log reads address the notebook by owner and slug and send no `versionLabel` (a version number is not a label; Kaggle answers 404, and `fakeKaggle` answers 404 for any kernel read with one); `KernelVersion` is only the `download_kernel_output` `versionNumber`. The tracked `save_kernel` job ends through `kaggle`'s `pollRemote` (also when its notebook is gone or never ran, see `../kaggle/AGENTS.md`); the untracked path reads the status itself. `ReadKernelLog` reads the latest session's log (a live event stream, bounded by idle time, up to 16 MiB); only the scrubbed last 64 KiB is stored. `fakeKaggle` answers `save_kernel` and `create_dataset` refs as real Kaggle does (`/code/...`, `/datasets/...`); nothing here parses them. `ReadGGUFInfo` reads only the header with fixed caps.
- Driver refusals: `ErrDesktopReadOnly` (read-only desktop) and `ErrKaggleRefused` (a `kaggle.CheckGrants` refusal, wrapped by the server adapter) make the run wait with one `warn` per code (`kaggle_unavailable`, `desktop_readonly`, `kaggle_refused`; `Remote.BlockedCode` holds the current one). Before the notebook is submitted, a read-only desktop or a refused permission fails the run at once (`TestOrchestratorRefusalBeforeSubmitFailsAtOnce`). After submission the run keeps waiting (`TestOrchestratorRefusalAfterSubmitWaits`). A wait longer than 6 h fails the run with its code in every state except `running` and `cleaning`: before the notebook runs (this includes `starting` after `save_kernel` was admitted) and while downloading. `running` has no six-hour limit; the deadline below applies there.
- Deadline: the run's deadline is remote start + session + 20 min (`deadlineSlack`). Past it, one status read decides: a terminal answer ends the run, any other successful answer ends it with `remote_timeout`. A failed read keeps the run waiting up to 30 min past the deadline (`lateReadGrace`), then ends it with `remote_timeout` (`TestOrchestratorStatusReadFailureAfterDeadline`).
- Cancel: `Cancel` stores `cancel_requested`, never calls Kaggle and returns a run in `cleaning` or a terminal state unchanged (`TestOrchestratorCancelInCleaningAndBeforeCleaning`). A stop stored before `cleaning` turns a succeeded end into `cancelled` (`cancelWins`) even when the results were checked; downloaded files and artifact rows stay until the run is deleted. Before submission, and in `downloading` or `verifying`, the run ends `cancelled` at once. After submission one remote cancel is tried, and tracking goes on until Kaggle reports the notebook ended.
- Cleaning: every run passes `cleaning`, which never waits for Kaggle. It waits while a local transfer job of the run is active or cannot be read (`TestOrchestratorJobReadErrorInCleaningWaits`). It removes the run's staged `r<run12>-` files; a failed removal is retried after the error wait, and after five failed rounds the names go into a `staged_left` warning and cleaning goes on (`TestOrchestratorStagedFileRemovalRetried`). The dataset, then the notebook, are deleted only with `allow_delete` and the run's delete flag; a failed delete warns `cleanup_failed`.
- Leftovers: `finishRun` lists a dataset or notebook only when it was kept, or its delete or check failed, and Kaggle may have it (`datasetMayExist`, `notebookMayExist`: an admitted create that Kaggle did not reject, or a known version or status). A create that Kaggle refused lists nothing and gets no delete (`TestOrchestratorLeftoversListOnlyWhatKaggleHas`).
- Downloads: before a transfer `checkRoom` checks `max_transfer_mb`, the storage cap and free disk. The copy is verified through `os.Root` with size and sha256 from the manifest, stored under names AuraGo generates, and recorded as copied in the same commit as the Kaggle job result, before the staged copy is removed. A restart after the copy never downloads the file again (`TestOrchestratorRestartAfterCopyBeforeRemoval`); a failed staged removal is only logged.
- Shared base GGUF: `base/<profile>-<revision12>-<converter>.gguf` with one `base_gguf` row per profile, base revision and converter (`llamacpp-<tag>`), shared by all runs. A stored file whose size and sha256 match its row is authoritative: a manifest declaring another size or hash fails the run with `checksum_mismatch` and leaves the file and row alone (`TestOrchestratorSharedBaseGGUFConflict`); a matching manifest reuses the file with the run's own `gguf_base` artifact row. Without a usable stored file, the run downloads a verified copy and registers it as the shared file. A run that finds its base GGUF invalid (unreadable or wrong architecture) warns `base_gguf_invalid`; it removes the file and row only when it stored them itself and no other run's artifact refers to the file, otherwise only its own artifact row goes (`TestOrchestratorBaseGGUFArchitectureDrop`). `RemoveRunFiles` never touches `base/`.

## Work Guidance

A new check gets a table row in `checks.go`, a flag only when it is row-level, a fixture test, and a message key handed to the UI locales. A new prompt text or schema change needs a `generate_test.go` case; keep the guard instruction first in every system message. A new job kind gets a `Runner.Start` call in `internal/server` that follows `chibi_sensei_files.go` (runtime store captured at start, stop on runtime shutdown).

A new run failure or warning code gets a UI message key and a row in the failure table of `documentation/chibi-sensei.md`. The server owns the HTTP shapes; keep `RunView`, `PreflightItem` and `Report` JSON in step with the HTTP contract.

## Verification

```
go test ./internal/chibisensei/... -count=1
go test ./internal/chibisensei/ -count=1 -run '(?i)Orchestrator'        # state machine and restart table against fakeKaggle
go test ./internal/chibisensei/ -count=1 -run '(?i)(Golden|ProofData)' -update   # rewrite goldens and proof data; review the diff
CHIBI_PROOF_OUT=<dir> CHIBI_PROOF_PROFILE=<profile id> go test ./internal/chibisensei/ -count=1 -run '^TestProofBundle$'
go test ./internal/chibisensei/trainer -count=1
```

`TestProofBundle` writes the data files, marker, `job.json` and notebook of one manual proof run (optional `CHIBI_PROOF_OWNER`, `CHIBI_PROOF_MACHINE_SHAPE`, `CHIBI_PROOF_RECIPE`, `CHIBI_PROOF_PRESET`, `CHIBI_PROOF_TIMEOUT_MINUTES`); it is skipped without `CHIBI_PROOF_OUT`. The trainer tests (`--selftest`, `--dry-run` with `CHIBI_FAKE_ENV=1`) need Python 3.10+ as `python3` or `python` on PATH and skip otherwise.
