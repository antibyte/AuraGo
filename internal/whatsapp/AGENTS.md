# WhatsApp channel

## Purpose

Owner-only WhatsApp channel over `go.mau.fi/whatsmeow` (WhatsApp Web multi-device). AuraGo is a linked companion device named "AuraGo". Stage 1 covers linking, the device store, the connection generation, status and the owner test message. Stage 2 adds the text channel: the inbound filter, the agent pipeline, the reply broker and the one owner-only send queue. Stage 3 adds media in both directions, the owner send API, the `send_whatsapp` tool and the `whatsapp` notification channel. Design: `plans/2026-10-31-whatsapp-integration-design.md`. Plan: `plans/2026-10-31-whatsapp-integration-plan.md`. Stage 2 plan: `plans/2026-10-31-whatsapp-2-text.md`. Stage 3 plan: `plans/2026-10-31-whatsapp-3-media-tools.md`.

## Ownership

- `client.go`: `waClient`, `deviceStore`, `backend`, the whatsmeow adapter (`newWhatsmeowClient` is the only `whatsmeow.NewClient` call), the auto-reconnect cap and the linked-device name and props. Stage 2 adds `MarkRead`, `SendChatPresence`, `OwnLID`, `PNForLID`, `LastSuccessfulConnect` and `GenerateMessageID`, and `SendMessage` takes the message ID the sender generated. Stage 3 adds `DownloadToFile` and `Upload` (which wraps `UploadReader`).
- `errors.go`: sentinel errors that the server maps to fixed HTTP codes. `ErrRecipientNotOnWhatsApp` is the owner-facing one (409 in the server); the sender wraps whatsmeow's error under it. `errNotOwnerRecipient` is internal.
- `store.go`: `<data_dir>/whatsapp/device.db`, modernc SQLite with `_pragma=foreign_keys(1)`, `_pragma=busy_timeout(5000)` and `_pragma=secure_delete(1)`, and the `sqlstore` dialect `sqlite`.
- `events.go`: `classifyEvent`, which maps a whatsmeow event to status state, error code, terminal and reconnect policy.
- `runtime.go`: the `Bot` generation (connect loop, backoff, health, owner test message, `Logout`), the inbound routing in `handleMessage` (offline cutoff, worker slots, drain on stop) and `ConfigState`.
- `recipients.go`: `ownerRecipients`, the single owner-recipient resolver, and the test message text. The sender adds the self-chat prefix, not this file.
- `cache.go`: `idCache`, the bounded ID caches: the sent-ID echo cache (5000 IDs, 20 min) and the dedupe cache of accepted IDs (2048 IDs, no TTL).
- `inbound.go`: `inboundFilter.accept` (design steps 2–8), owner resolution, the self-chat rule and the fixed drop codes.
- `pipeline.go`: `AgentDeps`, `pipeline.handle` (the `processUpdate` mirror for text and media), typing and the answer.
- `broker.go`: `whatsAppBroker`, the `agent.FeedbackBroker` for one owner turn; it captures TTS audio and YouTube videos for after the run.
- `send.go`: `sender`, the one outbound queue. `deliverText`, `deliverTextParts` and `deliverMedia` share the owner guard, the queue slot and `sendOne` (pacing, echo registration, delivery accounting). `caption` formats a media caption. Also `tokenBucket`.
- `media.go`: the download cap (`downloadMedia`, `cappedFile`), the MIME mapping (`mediaKindFor`), the upload (`uploadMedia`), the message builders (`mediaMessage`), the document name (`documentName`), and the ffmpeg command lines and runner (`voiceNoteArgs`, `mp3Args`, `runFFmpeg`, `convertedSize`, `convertToVoiceNote`, `oggOpusSeconds`).
- `inbound_media.go`: `readContent` and its content rules (ContextInfo, third-party content, quotes), transcription (`transcribeAudio`), vision (`describeImage`, `stageImage`) and document saving (`saveDocument`).
- `outbound_media.go`: answer images (`deliverAnswerImages`, `sendAnswerImage`, `openWorkspaceImage`) and captured TTS (`deliverCapturedAudio`, `openTTSFile`, `convertVoice`).
- `outbound_api.go`: the owner API used by other packages: `Bot.SendOwnerMessage`, `Bot.SendOwnerAttachment`, `Bot.OwnerSendReady`, and the gate `ownerSendAllowed`.
- `format.go`: `toWhatsApp`, the Markdown-to-WhatsApp conversion. `chunks.go`: `chunkText`, the rune-counting, fence-aware splitter.
- `link.go`, `qr.go`: `LinkSession` (one at a time, 3-minute TTL) and QR PNG data URIs through `internal/qrcode`.
- `log.go`, `mask.go`: whatsmeow-to-slog adapter and digit masking.
- Owned elsewhere:
  - `internal/server/whatsapp_runtime.go`, `whatsapp_handlers.go`: lifecycle, agent dependencies and HTTP; `whatsapp_backup.go`: the backup-walk skipper for the store directory.
  - `internal/integrationstatus/whatsapp.go`: passive status snapshot and drop counters.
  - `internal/tools/whatsapp_hook.go`, `whatsapp_send.go` and `notification.go`: the owner-send hook (`WhatsAppOwnerSender`), the `send_whatsapp` body and the `whatsapp` notification channel. `internal/server/whatsapp_tool.go` implements the hook.
  - `internal/config/whatsapp.go`: the `whatsapp:` section, E.164 rules, store and protected paths.
  - `internal/tools/protected_paths.go`: agent file-tool protection.
  - `ui/cfg/whatsapp.js`: Config section and link panel.
  - `internal/audit`: route manifests, network-client inventory and the SQLite backup exclusion.

## Local Contracts

- **One device owner per process.** At most one `Bot` or one `LinkSession` uses the device store. A link stops the Bot first. A session closes its client and store before `onFinish` runs, so the next Bot is the only user.
- **The device store is a credential.**
  - `<data_dir>/whatsapp/` is 0700 and `device.db` is 0600, both set by `fileutil.RestrictToOwner` (protected owner-only DACL on Windows).
  - Never in `config.SQLiteDatabasePaths` or backups. `device.db` is a documented entry in `internal/audit` `sqliteBackupExclusions`.
  - `config.WhatsAppProtectedPaths` lists `device.db` with `-wal`, `-shm` and `-journal`. `protectedSystemFilesFromConfig` returns them for agent file tools, outgoing attachments and Compose protection.
  - Shell and Python tools get no WhatsApp-specific deny: they keep exactly the vault's existing boundary (sandbox scope and the Danger Zone `allow_unsafe_host_execution` risk, which applies to `vault.bin` equally). The design's "file tools and the Python sandbox" wording is met through that equal treatment, recorded as a stage-1 deviation.
  - The store connection runs with `secure_delete`, and local removal (`removeLocalDevice`) deletes the device row, closes the store and then removes `device.db` and its `-wal`, `-shm` and `-journal` sidecars. Verify `local_removal_test.go`.
- **Owner-only sends.** Every text goes through `sender.deliverText`, `deliverTextParts` or `deliverToOwners`, and every media message through `sender.deliverMedia`. They all resolve recipients through `ownerRecipients` and refuse any recipient that is not one of its entries. The owner API sends to the owners of its own generation (`ownerRecipients(b.initial, …)`). Dedicated mode sends to `owner_numbers`, self-chat mode to the linked own JID. No API accepts arbitrary numbers. In `self_chat` mode every outgoing text starts with `self_chat_prefix`, once per chunk and on each caption (a media message without a caption carries none); the test message gets it from the sender too.
- **Inbound filter.** `inboundFilter.accept` runs design steps 2–8 in this order. Step 1, the type switch on `*events.Message` in `run()`, ignores `HistorySync` and every other event. A dropped message counts one fixed code and nothing else happens.
  - Step 2, the chat class: `status@broadcast` → `status`; other broadcast lists → `broadcast`; a newsletter chat or sender → `newsletter`; a group (`IsGroup` or `g.us`) → `group`; a bot sender → `unsupported_sender`.
  - Step 3, the kind. whatsmeow has already unwrapped the message, so the filter unwraps only a hand-built event. No content → `empty`; an edit, pin or revoke (`IsEdit` or `Info.Edit`) → `edit`; a protocol message → `protocol`; a reaction or encrypted reaction → `reaction`; any poll creation, update or result → `poll`. Only the kind is read, never the text.
  - An empty message ID → `empty_id`, because neither echo nor duplicate can be judged for it.
  - Step 4, echo: an ID in the sent cache → `echo`. Step 5, dedupe: an ID already accepted → `duplicate`.
  - Step 6, offline cutoff → `stale` (see below).
  - Step 7 (dedicated) or step 8 (self chat) decides the owner. Step 8 decides from the message source, with one exception from the text (`own_prefix`, see the self-chat rule).
- **Owner resolution (dedicated mode).** An own message (`IsFromMe`) → `from_me`. A `s.whatsapp.net` sender is the phone itself. A LID sender resolves, in order, through `SenderAlt` (used only when it is a phone JID, because whatsmeow also fills it with a LID), through `Store.LIDs` (`PNForLID`; an error or an empty result is a miss), and through the owner LIDs learned earlier. Nothing resolves → `unresolved_lid` with one masked WARN. A phone that is not in `owner_numbers` → `non_owner` with one masked INFO line, so each stranger message that reaches this step costs one masked log line. Each accepted owner message teaches its LID (`rememberOwnerLID`), so only LIDs of accepted owners are kept, and a stranger cannot teach one.
- **Self-chat rule (`self_chat` mode).** A message is accepted only when it is `IsFromMe`, the account is known and the chat is the own phone user or the own LID user; the owner is the linked account. An own-device copy (`DeviceSentMeta`) also needs its `DestinationJID` to be the own account, because whatsmeow falls back to the own account as `Chat` when a stanza has no recipient. An empty destination leaves the decision to the chat check. An unparseable or foreign destination is `not_self_chat`, even when `Chat` is the own chat. Messages from contacts never pass. This is the one place the filter reads text: a message those rules would accept is still dropped as `own_prefix` when its top-level text (or caption) starts with a non-empty `self_chat_prefix`. Every text and caption AuraGo sends in the self chat carries that prefix, so such a message is AuraGo's own echo, caught even after its ID has left the 20-minute sent cache. The check runs after the source rules and before the message is accepted or remembered for dedupe, so a contact's prefixed text stays `not_self_chat`. An empty prefix drops nothing, and dedicated mode never applies it. The cost is that the owner cannot start a note to themselves with the prefix; the default is a robot emoji and a space.
- **Offline cutoff.** While the connection's offline sync is unfinished (`!synced && !resumeSynced`), a message older than `LastSuccessfulConnect()` minus 10 minutes is `stale`. The reference is whatsmeow's login time, because the Bot's own `Connected` observation is not ordered against message dispatch (`plans/2026-10-31-whatsapp-2-text.md`, Q1). Message timestamps are server time, but `LastSuccessfulConnect` is the local clock: a local clock more than 10 minutes fast drops every queued message, and a clock that runs behind lets old ones through. NTP is assumed. Live messages after `OfflineSyncCompleted` are never compared with the local clock. A keepalive timeout clears `synced` but keeps the finished sync as `resumeSynced` until `KeepAliveRestored`. The flags belong to one login: `observeLogin` clears them when a message or an offline-sync event sees a `LastSuccessfulConnect` it has not seen before (`loginSeen`). That covers whatsmeow's forced reconnect after a failed keepalive, which emits no `Disconnected` and skips `resetConnection`; without it a laptop waking from a long sleep would run the commands queued during the outage. A late `Disconnected` of the previous connection can still clear `synced` after the new login's sync; the cutoff then stays anchored to the current login, so no stale message passes, and live messages are lost only with a local clock more than 10 minutes fast until the next `OfflineSyncCompleted`.
- **Echo cache and dedupe.** One sent-ID cache (5000 IDs, 20 min TTL) is shared by the filter's echo check and the sender. The sender generates the ID (`waClient.GenerateMessageID`) and adds it to the cache before `SendMessage(..., id)`, so an echo that races the call is already known; a failed send leaves its ID in the cache. whatsmeow's fan-out skips the sending device, so no echo is expected; the cache guards copies that arrive anyway. The dedupe cache holds accepted IDs only (2048, no TTL). A rejected message never enters it, so strangers' traffic in `self_chat` mode cannot evict owner IDs.
- **Single sender.** `sender.sendOne` is the only path to `SendMessage`, reached from `deliverText`, `deliverTextParts` and `deliverMedia`; `TestOnlyTheSenderCallsSendMessage` allows just `client.go` and `send.go`. In order:
  1. A cancelled context returns its error and counts nothing.
  2. No logged-in client → `ErrNotConnected`.
  3. Owner guard: the recipient must equal one `ownerRecipients` entry. Otherwise a masked WARN, `errNotOwnerRecipient`, nothing sent and nothing counted.
  4. `security.Scrub` runs before `toWhatsApp`. The order matters: a registered secret that holds `|` or `**` would otherwise be broken by the formatter before the scrub could match it. Then `chunkText` splits at 4000 runes minus the self-chat prefix. A caption (`caption`) gets the same formatting and prefix, and is cut to 1024 runes with `…` for answer images; owner text that does not fit a caption is returned whole and sent as a message of its own.
  5. The queue is one slot: a channel semaphore held for every chunk of a message. A send that waits for the slot gives up with its context.
  6. Pacing: a token bucket with burst 5 and one token per 3 s (20 per minute).
  7. Per message (each chunk of a text, or the one media message): `SendMessage` with plain `Conversation` text, which carries no link preview, or with the media message. Before the call the ID enters the echo cache; on success `MarkWhatsAppOutbound` runs. On failure, unless the context ended, it counts `MarkWhatsAppDeliveryFailure`, logs the masked error and stops the message. `ErrRecipientNotOnWhatsApp` is wrapped so the server can map it to 409.

  `deliverToOwners` sends to every owner, continues after a failure and returns the first error. `deliverTextParts` also reports whether a chunk reached WhatsApp, which is what `TextSent` is built from. `deliverMedia` runs steps 1–3, 5, 6 and 7 for one media message (step 4 formats text, and a caption is formatted by the caller through `caption`); the caller has uploaded the file.
- **Pipeline parity.** `pipeline.handle` mirrors `telegram.processUpdate` for text and media. In order:
  1. Config: the generation's snapshot. A nil config, egg mode or a changed `whatsapp` section drops the message (`no_config`, `egg_mode`, `config_changed`).
  2. **Owner re-check:** `in.Owner` must equal an `ownerRecipients` entry before anything else. The filter is not the only gate; a message that fails this check is dropped with a WARN.
  3. Read receipt for each message the pipeline handles, media included, only in dedicated mode with `send_read_receipts`.
  4. Budget tracking and the session. A session other than `default` gets no history manager. The session run is registered here, before any media is processed.
  5. Content: `readContent` reads the top level only (see Content order below). A failed voice message sends its notice and stops. A message with no input (a contact card without a vCard, for example) starts no turn and logs its kind (`image`, `audio`, `video`, `document`, `sticker`, `location`, `contact` or `other`) at INFO.
  6. Third-party content (forwarded, or a contact card): the marker `telegram.ForwardedContentMarker` goes into the isolated block, with no HumanInput, no slash command and no pending-question answer. HumanInput is also nil for a message without the owner's own words.
  7. A pending `question_user` takes the reply first, with `Source = tools.QuestionSourceWhatsApp`. Otherwise, or when the message is third-party, the owner gets "Please reply with one of the listed numbers."
  8. The session turn lock, then slash commands with `AllowOperator: true` (only from a message that is not third-party and carries one content type), then the Guardian (ThreatHigh blocks), then `security.IsolateExternalData`.
  9. History and the agent loop with `MessageSource: "whatsapp"` and `VoiceOutputActive: agent.GetVoiceMode()`.
  10. Captured TTS audio first, then the answer: `StripThinkingTags`, the Markdown images (see Answer media), `AppendMissingYouTubeLinks`, then the sender.

  Logs carry the owner's masked JID, message kinds and drop reasons, never message text.
- **Workers.** `handleMessage` runs the filter inline on whatsmeow's handler queue, under `eventMu`; a stopped generation counts nothing and starts nothing. Each accepted message gets one goroutine that takes one of five slots (`pipelineWorkers`, Telegram's default) or gives up when the generation ends. `run()` cancels the generation and waits for the workers before it closes the store. Two quick messages can therefore finish out of order; the session turn lock keeps the history consistent.
- **Broker and typing.** `whatsAppBroker` sends `question_user`, `budget_warning` and `budget_blocked` at once. `tool_start`, `error_recovery`, `api_retry` and `progress` are status updates, at most one per 10 seconds; the others are dropped. An `audio` event with a `file_path` (only the `tts` action sets one) and a `youtube_video` event with a URL are captured, at most five of each per run, and delivered after the run. A failed agent run drops them (see Answer media). `send_audio` and `generate_music` carry only web paths, so they are not captured; every other event is ignored. The broker logs nothing; the sender logs a failed delivery with its label and masked error only. Typing is `composing` at the start, refreshed every 8 seconds, and one `paused` when the run ends (not after a cancel). Whether the phone shows typing while presence is `unavailable` stays open until the Task 11 check.
- **Download cap.** `downloadMedia` refuses a declared `FileLength` over 50 MB before any download. The bytes then go through `cappedFile` into a 0600 temp file. `cappedFile` holds an `*os.File` in a named field: it has no `ReadFrom` and is not an `*os.File`, so whatsmeow neither preallocates nor bypasses the cap through `io.Copy`. The first write past 50 MB plus 32 bytes (the padding block and the MAC) trips it for good and cancels the download, so no other host is tried. The real size is checked again afterwards. Verify `TestDownloadMediaRefusesADeclaredSizeOverTheCap`, `TestDownloadMediaStopsWritingAtTheCap` and `TestCappedFileTripsForGoodAndCancels`.
- **MIME mapping and upload types.** `mediaKindFor` makes a file an image, video or audio message only when its content matches: a sniffed JPEG or PNG is an image; a sniffed MP4 with a `.mp4` or `.m4v` name is a video; `.mp3`, `.m4a`, `.aac`, `.ogg` and `.opus` names with a matching sniffed type are audio. Anything else is a document. Its MIME comes from the extension, else from the sniffed type, else `application/octet-stream`, without parameters (`documentMIME`). Uploads use the image, video, audio or document key family, and voice notes share the audio keys. Verify `TestMediaKindForMapsContentToMessageTypes` and `TestMediaMessageCopiesTheUploadAndMarksVoiceNotes`.
- **Voice notes and ffmpeg.** An outbound voice note (`voiceNoteArgs`) is Ogg Opus with `-application voip`, mono, 16 kHz and `-b:a 24k`. It is sent as PTT with MIME `audio/ogg; codecs=opus` and no caption. `Seconds` comes from `oggOpusSeconds` (the last granule minus the OpusHead pre-skip, rounded up); 0 means unknown and is for display only. Inbound voice messages and audio files, PTT or not, become mono 16 kHz MP3 at 64 kbit/s (`mp3Args`), which is enough for speech, and then go to `tools.TranscribeAudio`. WhatsApp has its own converter; Telegram's `ConvertOggToMp3Context` is unchanged. Every conversion runs with `-nostdin`, `-protocol_whitelist file,pipe`, a `-format_whitelist` of audio and video demuxers, `-fs` at the 50 MB limit and a 60 s timeout. Its output is discarded and never logged. An output at or above the limit is `ErrMediaTooLarge`, and an empty output fails (`convertedSize`): a truncated result is never a success. Verify `TestVoiceNoteArgsAreOpusMonoSixteenKilohertzVoip`, `TestMP3ArgsRestrictTheInputAndBoundTheOutput` and `TestConvertedSizeNeverReportsATruncatedResultAsSuccess`. The two ffmpeg tests, `TestConvertToMP3WithFFmpegRefusesContainersOutsideTheWhitelist` and `TestConvertToVoiceNoteWithFFmpeg`, skip without ffmpeg on `PATH`.
- **Content order.** `readContent` (`inbound_media.go`) reads only the top level of the unwrapped message; a nested wrapper that hides content stays `other`. Its order is: the text, joined with the caption; a voice message or audio file, transcribed (a failure sends `voiceFailedText` and stops); an image, described by the vision model (`[USER SENT AN IMAGE]`, with the caption as `[USER CAPTION/TEXT]`); a document, saved; a video and a sticker, which are never downloaded and get fixed placeholders; a location or live location, as coordinates; a contact card, as fenced third-party data; a quoted reply, as a prefix; and forwarded content, as the marker. `OwnerText` (HumanInput and routing) is the text, the caption or the transcript, read before the image, document and placeholder parts are added. Media from a non-owner is dropped by the filter and never downloaded (`TestPipelineNeverDownloadsMediaFromANonOwner`). A declared size over the cap is refused before the download (`TestPipelineRefusesOversizedMediaBeforeDownloading`).
- **Third-party content and quotes.** Forwarding is read from the ContextInfo of every content type: `IsForwarded`, `ForwardingScore > 0` or a newsletter forward in any one of them makes the message forwarded (`contextInfosOf`). A contact card is third-party too. Third-party content gets no HumanInput, no slash command and no pending-question answer, and a forwarded text carries the marker inside the isolated block. A slash command is read only from a message with one content type (`contentTypes`), so a forwarded multi-part message never runs one. A quoted reply adds one line, `[Reply to: …]`, in front of the input, from the first content type that quotes: the quoted text, else its caption, else `[kind]`, cut to 200 runes. The prefix is added only when the owner's message has input, and HumanInput and routing keep the owner's words. Contact cards are fenced: at most 5 vCards, 2000 runes each, in a fence longer than any backtick run inside the card. Verify `TestPipelineMarksForwardedMediaAsThirdParty`, `TestPipelineContactCardsNeverAnswerQuestions`, `TestPipelineQuotesRepliesInAShortPrefix` and `TestPipelineReadsForwardAndQuoteFromEveryContentType`.
- **Attachment saving.** A document is downloaded to a temp file that is removed on every path, then `media.SaveAttachmentReaderContext` stores it in `<workspace>/attachments`. The name comes from `documentName` (`media.SanitizeFileName`): reserved characters and `:` (NTFS streams) become `_`, as do control and format runes; leading and trailing spaces and trailing dots go; the base name is cut to about 100 bytes, with a short extension kept; `document` is used when nothing is left. `attachmentFileName` then adds the timestamp and turns spaces into underscores. The file is created with `O_EXCL` and `_1` to `_9` suffixes, so no file is overwritten. `media.SaveAttachmentContext` (URL downloads, Discord and Telegram) keeps its naming byte for byte. The model reads `[DATEI ANGEHÄNGT]: agent_workspace/workdir/attachments/<name>`, with the MIME type in parentheses when there is one (one line, invisible characters removed, at most 100 runes). Download and store failures have their own notices (`fileTooLargeText`, `fileFailedText`, `fileNotSavedText`). Verify `TestPipelineSavesDocumentsAsAttachments` and `TestSaveDocumentNeutralisesTheSendersFileNameAndMIME`.
- **Answer media.** After the agent run, captured TTS audio goes out first, then the answer, in Telegram's order (`bot.go:672-735`). `StripThinkingTags` runs, then `media.ExtractMarkdownImages`. The first `maxAnswerImages` (5) images of a reply are sent as image messages, with their alt text as caption cut to 1024 runes with `…`. Images beyond the first five are never fetched; they and any image that cannot be sent become `[Image: alt]` lines. A `/files/` URL opens through `tools.OpenOutgoingAttachment` (`openWorkspaceImage`) and must decode as an image of at most 40 million pixels. An http(s) URL is fetched by `media.DownloadAndSanitizeImageContext` into `<workspace>/images`, and the copy is removed after the send. Any other URL is not fetched. A file that is not a JPEG or PNG (a GIF or a WebP) goes as a document, so its bytes stay intact. `AppendMissingYouTubeLinks` then adds the captured YouTube links, and the text goes through the sender. A failed agent run drops the captured media with one fixed log line (`WhatsApp captured media dropped after a failed agent run`). Verify `TestPipelineSendsAnswerImagesAsImageMessages`, `TestPipelineFetchesAtMostFiveAnswerImages`, `TestPipelineSendsNoProtectedOrDataDirAnswerImages`, `TestPipelineAppendsMissingYouTubeLinks` and `TestPipelineDropsCapturedMediaAfterAFailedRunWithALogLine`.
- **TTS.** Only the `tts` action sets a `file_path`, and a captured one must lie inside `<data_dir>/tts`. `openTTSFile` checks the path lexically and then opens it through an `os.Root` on that folder, so a link that leads out is refused. It must be a regular file of at most 50 MB. In voice mode (`agent.GetVoiceMode()`) it becomes an Ogg voice note: ffmpeg reads a private copy made from the open handle, never the path again. A failed conversion, or no voice mode, sends the file as an audio file, with its kind from `mediaKindFor`. A refusal logs one fixed reason (`outside_tts_dir`, `tts_dir_unavailable`, `unreadable`, `not_a_file` or `too_large`). `send_audio` and `generate_music` events carry only web paths and are not sent. The `tts` action scrubs its text before synthesis (see `internal/agent/AGENTS.md`). Verify `TestPipelineSendsTTSAsVoiceNoteInVoiceMode` and `TestPipelineDeliversOnlyTTSFromTheDataDir`.
- **Owner API.** `Bot.SendOwnerMessage` and `Bot.SendOwnerAttachment` (`outbound_api.go`) send to the owner without answering a message; the `send_whatsapp` tool reaches `SendOwnerMessage` through the server's hook. `OwnerSendReady` reports a running, linked generation; readonly is not part of it. Every send passes `ownerSendAllowed` first, which reads the live configuration and fails closed. No live configuration, or egg mode, gives `ErrNotConnected`. `whatsapp.readonly` gives `ErrReadOnly`, checked before the generation match. A generation that no longer matches the live `whatsapp` section gives `ErrNotConnected`. The send's context ends with the caller's and with the generation's, so a stopped Bot never keeps a send running. A file comes only from `tools.OpenOutgoingAttachment`, and its size and kind are checked before anything is sent, so a refused file sends no text either. `SendOwnerAttachment` takes bytes AuraGo made itself, and its callers are the camera photo (`person_detect_alerts.go`) and the newspaper PDF (`newspaper_delivery.go`), both through `whatsAppOwnerAPI`. Text that does not fit as a caption (1024 runes after formatting, the self-chat prefix included), and the text of an audio file (which has no caption), goes first as a message of its own. The file is uploaded once and sent to each owner from the generation. `TextSent` is true once the text reached any owner: as any part of a message of its own, or as the caption of a media message that went out (a file that reaches owner A with its caption and fails for owner B still reports it, so a caller does not send the caption to A twice; owner B misses that send, which callers accept). Errors are wrapped in `safeOwnerError`: `Error()` is masked, and `errors.Is` still matches. Verify `TestSendOwnerFailsClosedWithoutALiveConfig`, `TestSendOwnerMessageRefusesInReadOnlyMode`, `TestOwnerSendEndsWithTheGeneration`, `TestOwnerSendErrorsAreMasked`, `TestSendOwnerMessageReportsTextSentWhenALaterPartFails` and `TestSendOwnerMessageOpensFilesOnlyThroughOutgoingAttachments`.
- **Send tool and notifications.** `send_whatsapp` (`internal/tools/whatsapp_send.go`) and the `whatsapp` notification channel both reach the owner through `SendOwnerMessage`, so both pass its gate. A notification is refused, not split, when its raw title, a newline and its message exceed `tools.WhatsAppMaxMessageRunes` (4000, pinned to `maxChunkRunes` by `TestNotificationLimitIsTheChunkLimit`). The count is taken before `Scrub`, which can lengthen text (`[redacted]` replaces a registered value), so a near-limit text that holds a short secret can still be split. The title stays on one bold line. A configured but unlinked device makes `send_whatsapp` `needs_setup` (runtime dependency unavailable), not "disabled by the administrator"; the agent side is in `internal/agent/AGENTS.md`.
- **Drop counters.** `dropped_non_owner` and `dropped_unresolved_lid` keep their own fields. Every other filter code is counted in `dropped_filtered`, keyed by the code: `status`, `broadcast`, `newsletter`, `group`, `unsupported_sender`, `empty`, `empty_id`, `edit`, `protocol`, `reaction`, `poll`, `echo`, `duplicate`, `stale`, `from_me`, `not_self_chat` and `own_prefix`. `messages_received` counts every `events.Message` before the filter, so dropped messages count there too. Counters survive generations. Pipeline-level drops are logged, not counted.
- **No valid owner.** In dedicated mode `ConfigState` reports `not_configured` unless at least one `owner_numbers` entry survives `config.NormalizeE164`; a Bot without one would drop every message as a stranger's. Self-chat mode needs no owner number.
- **Stopped generations stay silent.** Event handlers check the stop flag under `eventMu`, and the connect loop checks its context before each write. A stopped generation never writes status; the callers that stop it (`Logout`, a relink) write the next state themselves.
- **Link sessions.**
  - `LinkRequest.Validate` runs before the store is opened.
  - States: `waiting`, `qr`, `code`, `success`, `timeout`, `error`. A cancellation is `error` with code `cancelled`.
  - Phone linking asks WhatsApp for a pairing code; QR linking renders the payload as a PNG data URI.
- **Health.** `healthy` needs `OfflineSyncCompleted` on the current connection; a `Connected` that arrives after the sync also counts. A keepalive timeout forgets the sync until `KeepAliveRestored`. A healthy connection sends presence `unavailable` so the phone keeps notifications.
- **Reconnects have one owner per failure kind.**
  - whatsmeow reconnects `Disconnected` and `KeepAliveTimeout` itself. `AutoReconnectHook` caps its delay at 300 s. `StreamError` only marks the status `degraded`.
  - The Bot owns the first connect, store-open retries, connect errors and `ConnectFailure`, which whatsmeow does not retry. These retry with 5 s backoff doubling to 5 min, without limit. The Bot calls `Disconnect` before each reconnect.
  - `logged_out`, `conflict` (StreamReplaced) and `outdated` (ClientOutdated) wait for the user. `temp_banned` retries after WhatsApp's expiry; without an expiry it waits for the user.
- **Privacy.**
  - Debug output is dropped. Other whatsmeow lines are scrubbed and digit-masked, and protocol nodes are replaced by their tag.
  - Phone numbers and JIDs keep only their last four digits (`***1234`). Status holds masked values only.
  - QR payloads and pairing codes are never logged or stored. The browser keeps the QR and the code only in the Config panel's DOM.
  - Message text is never logged or put in status. The pipeline stores it in the session history through `InsertMessage`, as Telegram does; the `HumanInput` event ID becomes an opaque key (`personalityObservationKey`), so the chat number is not stored in clear as a turn ID.
  - Media logs carry the kind and one fixed code (`too_large`, `expired`, `cancelled` or `failed`), never a file name, path, URL, caption, transcript or vCard. ffmpeg's output is discarded, and a failed conversion logs only its code.
- **Release pin and licence.** whatsmeow is pinned by pseudo-version in `go.mod`; a "client outdated" outage needs a release with a newer pin. The module links GPL-3.0 `go.mau.fi/libsignal`, so distributed binaries are GPL-3.0 combined works (`licences/AGENTS.md`).
- **Stage scope.** Stage 2 (text) and stage 3 (media both ways, `send_whatsapp`, the `whatsapp` notification channel and voice output) are in: the inbound filter, the agent pipeline, the broker, the send queue and the owner send API. Stage 1's inbound counting stays in `handleEvent`, before the filter. Voice output is on: `agent.WithVoiceOutputSuppressed` is gone and `VoiceOutputActive` is `agent.GetVoiceMode()`. Stage 3b (camera alerts, EasyDrag and newspaper delivery, `plans/2026-10-31-whatsapp-3b-targets.md`) is done: the camera photo and the newspaper PDF go through `SendOwnerAttachment`, and the curated `notify.whatsapp` node covers the flows. `send_whatsapp` stays excluded from the generic flows node (`genericExcluded`, `internal/flows/catalog_generic.go`), because the curated node covers it and a generic node has no duplicate-text guard on a retry.
  - Stage 3 import cycle: `internal/whatsapp` already imports `internal/agent`, `internal/tools`, `internal/commands`, `internal/media` and `internal/telegram`. It uses five things from `internal/telegram`: `CapturedAudio` and `CapturedYouTubeVideo` (`broker.go`, `outbound_media.go`), `ForwardedContentMarker` and `AnalyzeImageContext` (`inbound_media.go`), and `AppendMissingYouTubeLinks` (`pipeline.go`). It does not use `telegram.ConvertOggToMp3Context`, which has no input whitelist and no output cap; WhatsApp converts with its own `convertToMP3`. `internal/discord` already imports `telegram` for `telegram.OriginLabel`, so this is the same kind of reuse. Therefore `internal/tools` must never import `internal/whatsapp`. The Bot is reached from `send_whatsapp` and notifications through the hook the server registers (`tools.WhatsAppOwnerSender`, implemented in `internal/server/whatsapp_tool.go`), never through an import, or the build cycles.
