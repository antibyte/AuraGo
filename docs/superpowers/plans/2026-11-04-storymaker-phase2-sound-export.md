# Storymaker Phase 2 (Sound and Export) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. The agent roster in the Setup section applies on top of that skill.

**Goal:** Storymaker's explainer videos get their sound and their spoken parts. Phase 2 improves the motion timing and adds a static motion lint. It adds narration with cloud and local voices, speech in the player (cues, speech bubbles, burned captions, lip-sync), sound effects and background music mixed in Go, and an export dialog that can hand the finished film to Video Studio.

**Architecture:** The same deterministic JavaScript player (`ui/js/storymaker/`) and the same export path as phase 1: a headless Chrome renders the frames and FFmpeg encodes them. Phase 2 adds four things. Narration is cut into one piece per sentence, each synthesised once and cached by a hash of provider, voice, language and text; a Go decoder and a 10 ms envelope trim each piece, and `AssembleBlock` joins the pieces with fixed pauses. The narrate and music jobs run on a second job manager, so an export never waits for them. The audio mix is a streaming pure-Go mixer (`internal/storymaker/render/mix.go`) with ducking, carve, impact dips and loudness; FFmpeg only encodes the result, as AAC 192k. Player timing and text layout use generated Unicode range tables instead of ICU-dependent browser APIs, so the same story places the same frames on every machine. Preview audio plays in the app, on the parent side; the iframe keeps no audio and no network access. Parallel render workers (part W) can be dropped without affecting the rest.

**Tech Stack:** Go (the existing toolchain; go-mp3 for MP3 decoding, `golang.org/x/text` for NFC), FFmpeg (AAC encoding and the loudness meter, the existing Video Studio encoder selection), plain classic-script JavaScript with no framework (`scripts/build-ui-bundles.js` concatenates the parts), Canvas2D, OffscreenCanvas and Path2D in workers, Web Audio in the app preview, Node 24 for the generator and the vm-based player tests, Chrome headless. Development-time only: the 25 sound effects were rendered once with earshot, and the three Unicode 16.0.0 text files are downloaded once in task M3. No build or runtime step renders or fetches anything.

The ten part files sit in `docs/superpowers/plans/2026-11-04-storymaker-phase2/`, next to this index: `part-M-motion.md`, `part-G-glyphs.md`, `part-N-narration.md`, `part-S-speech.md`, `part-E1-app-speech.md`, `part-A-audio.md`, `part-E2-app-sound.md`, `part-E3-export-handoff.md`, `part-W-workers.md` and `part-I-integration.md`. ## Setup for the executor

- **Worktrees.** Four worktrees, one per batch, as outline section 5 gives them: `.worktrees/storymaker-p2a`, `.worktrees/storymaker-p2b`, `.worktrees/storymaker-p2c` and `.worktrees/storymaker-p2d`, each on a branch of the same name. The start point is current main, which already holds this plan, so branch from it and not from an older commit. Batches land separately on main. Batch 2A starts with task M0. Before a task, check `git -C <main checkout> status --short -- <paths>`, because other sessions keep uncommitted edits in some files; outline section 2 ("Dirty files in the main checkout") says which files and what to do if they overlap. If a file that the outline lists is missing from the plan folder, stop and report it.
- **Agents.** Follow the user's roster, with no model overrides, as outline section 5 says. maker-agent writes and edits code. test-agent runs the tests and validation. reader-agent does the one combined review per batch, for spec and quality, and reports Critical and Important findings only. debug-agent investigates failures. Fixes always go back to maker-agent. security-agent reviews 2B, 2C and 2D as outline section 4 names them. docs-agent writes the docs, the contract, the spec and the plan. There is no re-review round after a fix: the controller checks the diff and reruns the tests the fix touched.
- **GitNexus.** The CLAUDE.md rules apply. Run `impact` before editing an existing symbol, report its callers, processes and risk, and warn on HIGH or CRITICAL. Run `detect_changes` before every commit. Outline section 5 gives the commands with the absolute runner path. Functions created by earlier tasks of this plan are not in the index yet, so an empty or `UNKNOWN` answer is not an all-clear: confirm the callers with a text search and say so in the commit body.
- **Go on the Windows box.** Set `GOCACHE=D:\dev-cache\go-build` and `GOTMPDIR=D:\tmp\go-build` (backslash form) in every shell, from the batch worktree.
- **Browser tests.** They run only with `AURAGO_RUN_BROWSER_SMOKE=1`, set on the browser line and removed after it. Chrome starts only from test binaries under `D:\tmp\go-build`, with the shell sandbox off, so run these lines through `go test`. A repo-built executable cannot start Chrome on this box. Further opt-ins are named in the parts where they are used.
- **Unicode data.** Task M3 downloads three Unicode 16.0.0 text files from unicode.org once, at development time. Nothing fetches them at runtime, and no external asset loads at runtime.
- **Commits.** One commit per task, with named paths only and the trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. `docs/` is git-ignored, so those paths need `git add -f`, and so does a new nested `AGENTS.md`. Never push unless the user asks.
- **Landing.** Follow outline section 5, "Landing a batch", in its order: rebase on main, rebuild the bundles, run the batch matrix, check main, and run `merge --ff-only` as its own step, never chained after the checks.

- A script applied every old/new edit of all 121 tasks in plan order to a scratch copy of main at commit 7b8a81195 or later, about 1100 edits, with no mismatch. Generators and locale scripts of the tasks ran there too. Red states before each task were not run, only batch ends.
- The tree was compiled and tested at the end of each batch. Results at the last run:

  | 2D | 197 passed | 44 passed | green, including TestStorymakerExportEndToEnd, TestStorymakerNarratedExportEndToEnd, TestStorymakerParityAppPlayerAndRenderPage, TestStorymakerAppRealServerBrowser and TestParallelParityBrowser |

  The 2A row comes from a run before the last small fixes, which touch only 2B tasks.
- Two internal/audit tests failed at every batch end and do not touch Storymaker: `TestUpdateConfigFallbackOnlyTrustedTransactionBackups` and `TestCredentialedHTTPClientsBindRedirectsToOrigin`. Outline section 4 records them. They were not rerun on an untouched main.
- The UCD data in that dry run came from Python's unicodedata 16.0.0, not from the real files M3 downloads. The audio in the end-to-end tests came from a stub synthesiser. No real voice or music provider ran, and nobody listened to anything.
- An independent review by seven lenses followed, with a skeptic per finding: 16 important findings confirmed and fixed, 5 refuted, 46 minor, most of them adopted. `reconcile.md` lists them.
- `TestRunRefusesReportsThatDisagreeWithTheJob` fails on main already, on most runs. Task M0 repairs it first.

## What needs the user

- **Listening.** Nobody has heard the output. The user's ears decide: the voice notes and rhythm factors; the sentence pause and the trim margins; the taste of the SFX set, especially `error` and `success`; the prosody with per-sentence synthesis, above all on cloud voices; the audible sentence gap of about 490 ms against the 350 ms the rule names; and the level of the non-hit SFX.
