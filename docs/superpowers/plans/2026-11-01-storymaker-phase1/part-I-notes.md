Where the fix differs from the reviewer's proposal:

- **SM-2 (CG).** The proposal (remove the bundle right after the source write) leaves the case where the removal itself fails: the new source stays, the old bundle stays, and the status is ok. Removing the bundle first closes it. Removing first would drop the bundle of a scene whose save is refused for a stale `If-Match`, so the precondition is checked before (the store's own check at write time stays). Failure states now: removal failed, nothing changed; any later step failed, new source without bundle ("has not been bundled yet", the render is blocked).
- **SM-1 (CG).** A fixed 15 minute cap would abort a legitimate slow download (the archive needs about 2.4 Mbit/s for that). The bounds are an idle limit that every received byte resets (started before the request, so the wait for headers counts) and `render.timeout_seconds` around the whole setup (also bounds one byte a minute). `OpenPage` keeps the job context: rod ties the browser's lifetime to it. The download lock `dlMu` is held for the download, so the stall also blocked the next export; it is free again after the limit.
- **SM-1 (SB).** The proposed placeholder URL is not enough (the verification said so too): the prefix stays in the page's DOM (`data-sm-base`, the script URLs) and the control path stays open, and a navigation to `file://` through DevTools would read files of the AuraGo user. The pipe removes the control path itself. `--remote-debugging-pipe` is old Chromium (the pinned revision 1321438 is Chromium 128); on Windows Chromium finds the pipe through `--remote-debugging-io-pipes=<read>,<write>` (inherited handles, `SysProcAttr.AdditionalInheritedHandles`), which Chrome 156 here accepts.

### What the pipe launcher does for the launcher it replaces

rod's `Launch()` only understands "DevTools listening on ws://...", so `startBrowserProcess` starts the process itself and keeps what the launcher did: flags from `newLauncher` (minus the port and the leakless helper, plus the pipe flag), stdout and stderr into a 4 KiB tail that goes into the start-up error (`launchIssue` still sees "No usable sandbox" and "shared libraries"), a 60 s start-up limit (kills a silent browser), `Close` = close the input (the browser quits when its input ends, so a crashed AuraGo leaves no browser behind), wait 5 s, kill the process group (Unix) or the tree (`taskkill /T`, Windows), remove the profile with retries. `browserProcess.PID()` replaces `session.l.PID()` (one spike test). `newLauncher` lost its unused context parameter. Only `probeLaunch` and `openRodSession` start a render browser; the test harness browsers in `internal/server` launch their own Chrome for the app side and are untouched.

### I2: one failed run of `TestStorymakerAppRealServerBrowser` (the no-frame watchdog)

The reported failure: the export of the gated real-server tour failed once, on a loaded box with an `h264_qsv` encoder (the start screen had taken 8 s and 21 s), and passed on the rerun. The log of that run was not kept, so the cause below is derived from the code and proven with a deterministic test, not read off that run.

- **What the restart does not do.** On `FrameRestart`, `accept` calls `onFrameAccepted(-1)`, which resets the watchdog, and the page redraws frame 0 (`host-render.js`: `if (reply.restart) { n = 0; ... continue; }`). The restart adds no delay on the page side. That part of the report is right.
- **What was wrong.** The timer is armed in `onReport` and reset only in `onFrameAccepted`, which the ingest calls after `sink.WriteFrame` returned (and after the recovery, for a restart). So everything Go does inside `Ingest.Accept` for a frame that the page has already delivered counted against the page's 10 s: the pipe write to FFmpeg (bounded only by `ffmpegWriteTimeout`, 30 s), `hardwareSettle` (1.5 s after the first frame of a hardware encoder), and on a failed hardware encoder the wait for its exit (up to 2 s), `Discard`, and the first write to the replacement libx264 process, which blocks until that process has started and reads (the WinGet full build `ffmpeg.exe` is 227 MB; on a loaded Windows box with a virus scanner its start takes seconds). The watchdog is meant for "a code scene may be stuck"; here it fired with a healthy page and reported `code_error`. The page's own frame deadline (5 s) cannot catch this, it measures only `engine.render`. A box with a hardware encoder that fails mid-stream is exactly where these waits add up, which matches the one failure seen.
- **Fix** (`internal/storymaker/render/render.go`): `holdWatchdog` stops the timer when `accept` starts; `onFrameAccepted` (taken frame or restart) arms it again as before; a refused frame fails the job, which stops the timer for good. The watchdog now measures the page only: from the answer to a frame to the arrival of the next one. Go's own stalls stay bounded by `ffmpegWriteTimeout`, the 2 s exit wait, the render timeout and the 3 minute report wait. Callers of `accept` (grep): `onFrame` (the HTTP hook) and `driveScreenshots`; the screenshot transport's capture time stays inside the window because the hold ends with `accept`. GitNexus `impact` for `accept`: ambiguous name (13 candidates, none in this file resolved, risk UNKNOWN); for `onFrameAccepted` no callers resolved (UNKNOWN); the two callers above are from grep. `detect_changes --scope all` before the commit: 4 files, 4 symbols (`accept` and three test functions that sit next to the new test), 0 affected processes, risk low, not partial.
- **Alternatives not taken.** A page heartbeat needs a new request in the page, the listener and the contract for a problem that lives in Go. A longer window for the first frame after a restart covers only one of the Go-side waits (the plain 1.5 s settle and a slow FFmpeg write have the same effect).
- **Test** (`TestRunWatchdogIgnoresTheTimeGoSpendsOnAFrame`, two subtests; the watchdog is 800 ms and the Go side takes 1.6 s for one frame through `Deps.FrameObserver`): "a slow frame" (frame 5) and "the first frame after the software restart" (VAAPI device that does not exist, so the restart to libx264 happens, then the first frame after it is slow).
