# EasyDrag durable execution contract

This contract defines the first pure-local Runner path. Human approvals extend it under `2026-11-05-easydrag-durable-approval-contract.md`; effect receipts remain a separate slice. Runner integration and full testing were explicitly authorized on 2026-11-05, with processing kept disabled by default. The flagship checkpoint table and owning guides record implementation and verification boundaries. Activation and deployment are outside this change.

Existing `logic.wait` parks a live process slot; it is not durable. Existing run steps are bounded and sometimes truncated, and therefore cannot restore execution. Existing runs without a durable marker or checkpoint keep `FLOW_RESTARTED` cancellation on startup. No existing run is silently upgraded or replayed.

## First Runner slice

- `flows.durable_enabled` defaults to false for new and existing configurations. Enabling requires the existing runtime restart; live disabling fences new admissions, wakes and active ownership while retaining committed state. The configuration UI distinguishes the saved setting from observed readiness. A statically registered `logic.durable_wait` remains readable in stored graphs when processing is disabled; registration does not grant execution.
- Only published live runs with one manual trigger and verified built-in Set, If, Switch, Merge, Stop and persistent-wait steps qualify. Validate the entire graph, including disabled and unreachable nodes. Draft tests, simulation, selected-step execution, child calls, batches, tools, models, secrets, files, devices and network operations cannot enter this path. Ordinary waits retain their existing behavior.
- New admission uses the current published version. An admitted run keeps its original published revision, authenticated snapshot and admission-time mission owner. Publishing v2 neither replaces nor blocks an already waiting v1 run. Recovery requires its unchanged retained v1 record and the same currently authorized flow/mission owner; missing or contradictory evidence blocks it. The original graph, output, wait, deadline, location and budgets remain unchanged. This grants no general right to start historical versions.
- Preserve the original absolute deadline, execution identity, outputs, edge/port state, taint and budgets. A named time zone must be reconstructable. Local or custom locations require an AST-proven zone-independent graph; a fixed current offset is insufficient for expressions that parse historical dates. Date filters and date-dependent or dynamically unclear conditions are excluded from that alternative. Time-zone rule versions are not pinned. Unsupported payloads stay blocked and retained.
- A committed wait releases the physical worker/global slot and retains its per-flow reservation. Recovery joins the existing fair queue with the same run ID, without a second reservation. Generation/owner CAS and active lease renewal fence stale workers. Never publish or persist after losing ownership. Committed completed pure steps do not repeat; pure computation not yet committed may repeat after process loss.
- Register revocation before checking current mission authority. Recheck flow/mission enablement, both read-only gates, exact owner and published identity at admission, wake and execution. Authority, history and user hooks run outside Runner, flow and SQLite locks. The private local Vault key provider is the narrow exception: it holds the checkpoint admission write lock through the empty-store proof and first encrypted insert, and must never reenter flow, Runner or policy code. A publication already past its authority check may finish concurrently with disable; publication itself does not authorize a run.
- Waiting and uncertain commits are not terminal events. Keep an existing event stream open while waiting; after a process restart, fetch the authoritative run/steps and reconnect with the same ID and cursor. Event history is not the recovery source and has no invented cross-store high-water mark.
- The flow journal projects payload-free history through a reserved run-ID-bound namespace. Projection is idempotent and terminal-monotone, never invokes ordinary completion follow-ups, dependent missions, Planner callbacks or notifications. JSON Mission run counters remain unchanged because an exactly-once update across the two stores is not established. Only that reserved namespace bypasses early legacy zombie cleanup; unavailable or missing source evidence remains unknown.
- Nonterminal durable history is annotated when read through the Mission Manager: missing, mismatched or unavailable source becomes `unknown` with separate `last_known_status`. Check a bounded page under one deadline, after releasing history/manager locks, for both HTTP and agent output. Confirmed terminal history remains valid after ordinary source-run retention. No source probe mutates history or dispatches completion actions.
- Observed capability/status exposes fixed reasons, nullable counts, generation, wake time and deadline, never checkpoint payloads. Explicit generation-fenced cancellation remains available when durable processing is off and the flow service exists. Stop retains the read-only/app-lock exception with normal administrator and existing Origin/CSRF checks (session POSTs require Origin; authenticated Desktop bearer tokens retain their existing CSRF exception); it cannot enable, wake or restore. Global `flows.enabled: false` boots without the service and reports unavailable rather than claiming cancellation succeeded.
- A Mission Control aggregate Stop refuses before any effect if a durable run or retained legacy checkpoint is involved. It directs the user to the individual run's generation-checked Stop. Ordinary aggregate stops retain existing behavior; no partial aggregate success or automatic retry is claimed.

External-effect receipts, human approval endpoints and durable child/batch execution below remain separate future slices. No general exactly-once promise follows from pure-run recovery.

## Storage and migration

- Schema v2 already introduced the private `flow_checkpoints` table; schemas v3–v5 added composition, organization and group compatibility. The Runner slice reuses that checkpoint table and raises the store to v6 with immutable `flow_runs.durable` and `flow_runs.durable_mission_id`. Set both only in actual durable admission, in the same transaction; ordinary public run creation cannot forge them. Old rows default to false/empty. A checkpoint without the marker remains incompatible, retained and explicitly cancellable. Both fields survive terminal checkpoint deletion so history retains the original owner even if the flow is later reassigned.
- Before changing an on-disk v5 database, take and verify a consistent SQLite backup including WAL state; fail closed without touching the original if backup or migration fails. Migrate in one transaction, update the version last, verify the v6 column contract and reject newer schemas. Test populated v5/WAL state, statement failures, old private ciphertext preservation and actual C10/v5-binary rejection. Keep the existing v1–v5 migration tests. Never treat the unused `checkpoint_json` column as executable state.
- Reuse the checkpoint row keyed by `run_id`, generation, state, authenticated payload, timestamps and absolute deadline. The first Runner payload version is 2; old private v1 payloads cannot silently acquire missing execution context. Commit checkpoint, step and run status together. Compare-and-swap on generation; a stale writer changes nothing. Before replacing or automatically deleting an existing generation, authenticate its ciphertext with the currently available key; missing or replaced keys retain the prior checkpoint and cannot silently re-key it. Explicit generation-fenced user cancellation remains key-independent. Later effect/gate slices need separately reviewed receipt and pending-gate tables with foreign keys and unique identities. Their transitions must share the coordinator transaction.
- Checkpoint payload contains the immutable published document/revision and definition versions (and future child references), trigger type/data, run ID/mode/start/deadline, location and taint roots, coordinator node status, ordered edge states by stable edge identity, exact accepted outputs by node key, selected ports, error/stop outcome, output and storage budget counters, invocation path and iteration position. Preserve inputs/outputs in full; never use `StepRecord` previews. Rebuild topological order and ready queue deterministically, verifying stored edge identities, definitions and budget totals against the pinned graph. Never re-run completed nodes merely to reconstruct state.
- At a suspension boundary, stop launching new nodes and drain in-flight work to a quiescent point. Record unresolved edge/node states and the gate in the same transaction; no goroutine or parked global slot remains for a durable run. If a worker cannot finish safely, record its outward effect as uncertain and require reconciliation; do not pretend a snapshot is quiescent. Bound all encodings before commit; reject the suspend with a visible capacity error if full-fidelity data cannot fit. The original run must stop safely rather than write a partial checkpoint.
- Checkpoints can contain personal and untrusted data. Encrypt payloads with a fresh nonce and an authenticated key protected by the Vault; use associated data binding run ID, version and generation. The server resolves the key, not the flow model. Never put Vault secret values or resolved credential-bearing request parameters in checkpoints, receipts, logs, exports, events or error text. If safe reconstruction needs one, resolve it again only after permission checks; otherwise refuse suspension. Do not rely on redaction to produce executable state. A locked/unavailable Vault leaves the run paused, never starts it with empty data. Access and cleanup follow the same administrator and file permissions as flows.db; no checkpoint is exposed by ordinary run APIs.

## Later slices: receipts and effects

- Operation identity is `(run_id, invocation_path, node_id, item_index)`, with an explicit root invocation and non-iterated sentinel. Attempts are not part of identity. Derive a stable opaque integration idempotency key from this identity; do not include user data or credentials. A unique constraint prevents duplicate logical actions across concurrent retries/resumes. Receipt payload holds only bounded, non-secret provider identifiers and result/uncertainty metadata.
- Each effectful definition declares `safe_retry`, `idempotency_key`, or `manual_reconciliation`; absent/unknown metadata means `manual_reconciliation`. Never infer safety from a category or from a successful simulation. Recheck the live tool grants, read-only gates, provider configuration, destination/taint fences and budget immediately before every dispatch and every resumed attempt. A disabled capability blocks rather than bypasses a checkpoint.
- Before an effect dispatch, CAS a receipt from absent/ready to `dispatching` and commit it together with the coordinator generation. Only the owner of that committed generation may dispatch. After a confirmed provider response, commit `confirmed` and the full output/port transition atomically before successors run. An explicit failure that proves no effect occurred can become `failed_safe`; a timeout, cancellation, process loss or ambiguous provider result after dispatch is `uncertain`. For `idempotency_key`, retry only if that integration explicitly guarantees the same key covers the same operation and retention period; otherwise require a human reconciliation decision. An idempotent API may still return an uncertain outcome after key expiration. Arbitrary services never get an exactly-once claim.
- A crash after dispatch but before confirmation is uncertain even if the user never saw a success. Reconciliation must explicitly record either verified completion plus output, or authorization to retry after acknowledging possible duplication; the decision uses the same CAS and audit rules as approval. A duplicate request receives the existing terminal decision, never dispatches again.

## Later slices: approval transitions and authority

`queued → running → waiting | approval_pending | uncertain → queued → running → success | error | cancelled`. A gate has its own `pending → approved | rejected | expired | cancelled` transition; no terminal gate changes again. Timeout/rejection follow an explicit configured branch or stop, never silently approve. A resume request carries expected checkpoint generation and gate ID; one transaction verifies both, records actor/time/decision, completes the gate and claims the next generation. Duplicate or simultaneous requests return the committed outcome without advancing twice. Timed wakeups use the same transaction and generation check; pending wake indexes are scanned on startup and after clock changes. The original absolute run deadline continues across restart and wait.

Approvals require an authenticated, authorized administrator session and normal CSRF protection at decision time; notification links only open the application and never authorize action. Recheck current access, flow enablement and all tool permissions when waking or resuming, not just at approval creation. Record bounded actor and decision metadata without notification tokens or content. Expired, disabled, deleted, revoked or incompatible runs stay blocked or take the documented timeout/cancel path, never auto-execute. Cancellation atomically closes gates, prevents future claims and records uncertainty for any dispatched effect. A restored run enters the existing fair runner queues and must obtain a global slot; waiting runs do not occupy one.

## Limits, retention and restart

- Current pure-run caps: existing 500 nodes, 2,000 edges, 2 MiB document and 32 MiB total encoded outputs per run; at most 40 MiB encrypted checkpoint per run, 64 admitted recoverable runs globally (including durable runs before their first checkpoint), and 512 MiB total checkpoint data. Validate exact encoded size and aggregate quota transactionally before every checkpoint update, including replacement accounting. No truncation or eviction of active checkpoints. Later receipts and pending approvals require explicit additional bounds. The byte-boundary arithmetic is tested separately from disk-load qualification; changing limits requires a reviewed contract, not hidden growth.
- Keep pinned versions and encrypted checkpoints while a run is recoverable. The first slice atomically deletes its checkpoint when committing a terminal result, while retaining the durable run marker and bounded history. Later receipts and approval decisions need their own terminal retention contract. Ordinary pruning must not delete active waits, unresolved state or pinned versions. Make limits observable without exposing payloads; quota exhaustion must not evict other runs.
- Startup reconciles only valid new-version pure checkpoints and schedules their waits through the existing queue. A lease/generation prevents two workers from owning one run. Existing uncheckpointed queued/running/waiting rows still follow `MarkInterruptedRuns`. Corrupt, unverifiable, unsupported-version or undecryptable checkpoints are reported and remain blocked; they never silently become an empty graph. Recovery is bounded and cannot prevent HTTP readiness indefinitely. Later approval/receipt recovery must rehydrate verified gates and classify interrupted dispatch as uncertain before resuming; expired leases alone never authorize an external resend.

## Implementation boundary and verification

Verification combines private storage/coordinator tests with actual Runner admission, scheduler, cancellation, shutdown and history tests. Actual subprocess exits prove waiting/active-step recovery with the same identity and no repeated committed steps. SQLite rollback and post-commit event-loss cases cover transactional boundaries; concurrent claims, lease loss, late workers, fair queuing, original deadlines, disable/delete/shutdown, key/capacity/corruption and history-outage cases cover ownership and recovery. A driver-level ambiguous response after a successful SQLite commit is not directly injected; private coordinator tests and the separate committed/uncommitted Runner boundaries provide narrower evidence. Configuration/HTTP authority, genuine locale parity, both themes and narrow windows require the corresponding tests, followed by exact clean-checkout Linux race checks.

Only subsequent slices add receipts around explicitly qualified integrations and authenticated approval gates. Typed subflows and bounded iteration may use durable invocation identity after their corresponding checkpoint/receipt tests pass; version retention, cross-version cycle detection, maximum depth/items, shared budgets and parent cancellation are prerequisites.

Inject crashes before and after transaction commit, dispatch, response, receipt, gate decision, wait scheduling and resume claim. Verify a completed pure node is never rerun; no external effect repeats after ambiguous dispatch; known-idempotent retries use one key; duplicate approvals/resumes and timer races yield one transition; changed grants block resume; cancellation prevents future dispatch; out-of-space, corruption, missing key, stale version and quota exhaustion fail closed without deleting unrelated runs. Exercise concurrent workers and SQLite write failures, restart with both v1/legacy and new rows, retention with active receipts, and Linux race tests. Server tests must prove admin/CSRF authorization and notification links cannot approve by themselves. Hardware/integration acceptance stays separate from local fake-provider tests.
